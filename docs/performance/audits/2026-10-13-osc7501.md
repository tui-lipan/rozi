# OSC 7501 implementation verification

Target: [OSC 7501 revision 0.4](https://www.superlogical.com/rex/docs/build/program-status),
October 10, 2026. The official page was reread on October 13; it still specifies revision 0.4.
No normative target change was needed.

The framework owns decoding, a 256-record terminal store, ordered lifecycle changes and query
responses. Rozi transports complete snapshots separately from runtime metadata and projects one
Activity summary per pane. Public agent states, native hooks, publisher ownership and resurrection
remain independent. The session protocol is 29.

## Parser throughput

Final framework measurements from [tui-lipan #333](https://github.com/tui-lipan/tui-lipan/pull/333),
shipped in 0.22.6, on Linux x86_64, Rust 1.96.1, release profile, 200-column by 60-row terminal:

```sh
cargo bench --bench terminal_ingest --features terminal -- program_status_ingest \
  --sample-size 30 --warm-up-time 1 --measurement-time 3
```

| Input | Disabled, empty store | Disabled, retained record | Enabled |
| --- | ---: | ---: | ---: |
| Ordinary output, 256 KiB | 4.2782 ms | 4.3092 ms | 4.2836 ms |
| 1,000 progress reports | 893.21 µs | 967.77 µs | 1.2479 ms |

The ordinary-output enabled and empty-disabled point estimates differ by approximately 0.13%.
Their 95% confidence intervals overlap: disabled 4.2257–4.3298 ms, enabled 4.2493–4.3209 ms.
This benchmark does not establish meaningful ordinary-output overhead. Enabled progress ingestion
processed approximately 801,000 reports/second. These are final framework ingestion measurements,
not end-to-end UI throughput. Ground-state scanning uses memchr; ordinary output does not allocate
records or snapshots. Server tests verify that a burst of 100 progress changes retains the latest
snapshot while suppressing intermediate transport updates. Message/progress synchronization is
limited to one update per 100 ms; state changes and clears bypass that delay. Duplicate effective
snapshots are suppressed. Snapshot text uses shared immutable strings.

## Regression coverage

Framework tests cover BEL/ST, fragmented and batched sequences, hard wire/text/ID limits, malformed
pairs, repeated keys, unknown fields, invalid UTF-8/base64/control text, complete replacement,
hierarchy and inherited apps, prefix-safe clearing, update order, capacity eviction, repeated
prompts, exit cleanup, RIS, DECSTR, alternate screens, resize, opt-in queries and OSC/DA reply order.

Rozi tests cover generic error classification, custom statuses, duration, ranking and failure glyphs;
OSC coexistence with detected agents, generic status and both publisher kinds; publisher preservation
through OSC clearing; stale generations and revisions; independent client attention; detached server
storage; progress coalescing; and the pane-creation/layout race. A real PTY integration test exercises
two clients, detach/reattach, separate pane identities and keep-open shell replacement.

Both repositories pass formatting, full test suites, strict Clippy, builds and diff checks. Framework
terminal-only checking and both repositories' Cargo deny checks pass. Cargo audit reports no
vulnerabilities; existing allowed unmaintained dependencies remain (ttf-parser in Rozi, four warnings
in the framework's all-feature graph).

## Live review

An isolated named session was opened in two independently owned Ghostty windows on Linux/Hyprland.
Each outer window was verified at 940 × 720 pixels; application and host captures were inspected.
Working progress, blocked, error, done and idle rendered in Activity. Generic `rozi status error`
coexisted with the OSC summary. An OSC-only `app=codex` pane did not appear in the agent list.
Both clients detached; with the server reporting zero clients, the producer emitted a new error.
Reattachment recovered the terminal's current status. Owned servers, producers and host windows
were cleaned up after review. Scratch captures and runtime data are outside the repository.

The review exposed a status arriving before a follower's pane layout. The server now repeats the
current snapshot immediately after the layout that first introduces that pane/generation. A server
regression and a second two-window run verify this ordering.

Live Windows/macOS testing was unavailable on this Linux host. This remains an explicit platform
verification limitation. No new OS-specific behavior was introduced.

## Released dependency and attach bounds

The Activity correction (#158) is merged into master. The integration consumes registry
tui-lipan 0.22.7, matching current master and including the final #333 fixes shipped in 0.22.6.
Cargo.lock records registry sources and
checksums; no Git pin, path override or Cargo-deny Git allowance remains.

Initial attachment carries pane identities and runtime metadata in the manifest, then streams OSC
snapshots per pane through the existing attach scheduler. Baselines are marked explicitly and
initialize presentation without historical attention or notifications. The 4 MiB send window bounds
queued replay and OSC data; only the current OSC frame is retained when the client stalls. A legal
snapshot enlarged by JSON escaping may exceed the normal 1 MiB per-tick budget; one atomic frame
is admitted at the start of a tick while remaining within the send window.

A socket-backed regression fills sixteen panes with 256 maximum-length legal records each, including
an escaped snapshot larger than the per-tick budget. The aggregate exceeds the 8 MiB frame limit.
It verifies a small Attached manifest, stalled-client backpressure, complete per-pane baselines and
successful draining without disconnect. The real PTY detach/reattach and keep-open regression
uses these streamed baselines.

Notification cooldowns are consumed only when a desktop notification or sound is dispatched,
after eligibility and the existing sound throttle checks. Regressions cover attended, DND,
follower, disabled delivery, sound-throttled and initial-attach transitions followed immediately by an unattended
error, including the actual Error sound cue and suppression after a delivered alert.
