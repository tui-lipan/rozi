This same-application, same-machine comparison changed only the framework. It attributed the

### Scrollback search

The pre-search-optimization 16-pane full scans were 35.604 ms sparse, 49.320 ms dense, and
34.637 ms with no match.

Phase 3a, compared with `--baseline before`, produced:

| 16-pane full scan | Phase 3a estimate | Change |
| --- | ---: | ---: |

| Sparse | 35.899 ms | +0.83% |

The sparse and no-match movement is noise. A complete scan still exceeded the 16 ms stop gate.
Phase 3a therefore did not satisfy input-latency acceptance, and Phase 3c was implemented.

| --- | ---: |
| Sparse | 205.45-206.70 µs |

All three were below 16 ms. These are Criterion estimate intervals, not p95 latency. Aggregate

### Server fairness

With sustainable continuous deterministic PTY ingress, key-to-helper acknowledgement had a
2.3376 ms estimate and a 2.3260-2.3512 ms Criterion estimate interval.

## Follow-up: asynchronous resurrection at `9f66a6a`

At `9f66a6a`, snapshots captured pane replay bytes on the server loop and handed the write, sync,
and rename to a worker. `last_blocking_us` reports the time the loop was held. The Criterion figure
covers the whole attempt.

| Panes | History | Whole attempt | Server-loop blocking | Moved off the loop |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 0 | 3.409 ms | 0.12-0.31 ms | ~93% |
| 16 | 0 | 34.494 ms | 2.2-3.6 ms | ~93% |
| 16 | 1,000 | 111.41 ms | 33.1-37.0 ms | ~69% |
| 8 | 5,000 | 109.34 ms | 83.9-98.4 ms | ~20% |
| 16 | 5,000 | 237.08 ms | 160.9-178.1 ms | ~28% |

This did not deliver the predicted result for the motivating case. The design assumed that `fsync`
dominated a snapshot, so moving the write would remove most of the stall. The measurement showed
that export dominated at 5,000 retained rows. Export could not leave the loop because it needed the
live `TerminalScreen`. The worst case improved from roughly 208 ms of blocking to roughly 170 ms.
The reduction was smaller than in the other cases.

Retained history shaped the result more than pane count. With little scrollback, the loop keeps only
~7% of the work. At 5,000 rows, it keeps most of it. The change therefore helps least where
snapshots cost the most.

Export cost followed the same pattern as the scrollback-search finding. The 16 panes x 5,000 rows x
250 columns case is 20M cells, and ~170 ms over them is ~8.5 ns each. This is slower than search's
~1.8 ns because the replay path emits SGR runs instead of plain text. It uses the allocation-free
`push_cell_text` path, so no further allocation reduction was available there.

Two options remain. The next section measures the first. The second was not implemented:

- **Skip unchanged panes.** A snapshot re-exports every pane even though a typical session has one
  or two active panes and a dozen idle ones.
- **Bound persisted history.** Persisting fewer rows per pane than the live scrollback retains is a
  policy decision with a user-visible trade-off.

## Follow-up: replay reuse for unchanged panes at `4d45cf4`

Each pane carried a content generation. A snapshot hard-linked the replay file from the last
successful snapshot when that generation still matched. The fixture and method were the same as
above, with one pane changed per iteration.

| Panes | History | Whole attempt | Server-loop blocking |
| ---: | ---: | ---: | ---: |
| 1 | 0 | 3.375 ms | 0.13-0.28 ms |
| 1 | 1,000 | 5.780 ms | 2.09-3.46 ms |
| 1 | 5,000 | 15.578 ms | 10.18-14.90 ms |
| 8 | 0 | 4.160 ms | 0.12-0.30 ms |
| 8 | 1,000 | 6.662 ms | 2.29-3.90 ms |
| 8 | 5,000 | 16.571 ms | 10.75-13.45 ms |
| 16 | 0 | 4.753 ms | 0.12-0.27 ms |
| 16 | 1,000 | 7.525 ms | 2.34-4.12 ms |
| 16 | 5,000 | 16.876 ms | 10.68-12.03 ms |

Three distinct numbers appear above and are easy to conflate. For 16 panes at 5,000 rows:

```text
Criterion estimate (whole attempt):        16.876 ms
Observed server-loop blocking range:       10.68-12.03 ms
Maximum recorded server-loop blocking:     12.03 ms
```

Maximum recorded server-loop blocking is the main metric for this work because it bounds input
latency. The Criterion estimate measures throughput for a whole attempt, including the worker's
durable write. That write no longer holds the loop. Comparisons with the pre-async numbers must use
the blocking figure on both sides. The original synchronous implementation had no distinction
because its whole attempt *was* the blocking.

At the measured revision, retained history drove cost more than pane count. One pane at 5,000 rows
cost 15.6 ms, and 16 panes at 5,000 rows cost 16.9 ms. Fifteen of the sixteen panes used links
instead of exports.

Against the original synchronous behaviour, maximum server-loop blocking for the 16-pane 5,000-row
case went from 207.730 ms to 12.03 ms, about 17x. It was then within the same order as the 2.34 ms
key round trip. Previously, it was roughly 90x that round trip.

The benchmark changes exactly one pane per iteration. This matches a session where one pane is busy
and the rest are idle. Reuse pays off in proportion to the number of unchanged panes. A session
where every pane is actively producing output still re-exports every pane and returns to the
previous section's numbers. Those numbers are the ceiling for this method. The optimization removes
redundant work. It does not make export cheaper.

The reuse path can silently lose scrollback, so structural checks guard it. `ServerPane`'s terminal
is private. Callers reach it through `screen_mut`, which bumps the generation, or
`screen_without_change` for operations that need `&mut` and leave persisted content identical.

The measured implementation treated reused replay files as immutable artifacts identified by pane
and content generation. Tests in `src/session/server/resurrect.rs` covered these invariants:

1. A published replay file is never modified in place. Writes only ever create files in the
   snapshot's own temporary directory.
2. Every file and link is in place before the manifest is published, and publication is one atomic
   rename.
3. Reuse claims are recorded only after a successful write, and dropped entirely on any failure.
4. A missing reuse source degrades to a full export *in the same attempt*: existence is confirmed
   during capture, on the server loop, where a screen is still available to export from. The worker
   has no such fallback, so the check cannot be left to it.
5. If hard-linking is unavailable - a filesystem without it, or a snapshot root spanning a mount
   point - the write falls back to copying.
6. Restore reads file contents through manifest references and never depends on inode identity, so
   carrying bytes forward by link is invisible to it.

Because links share an inode, a reused file outlives every directory it was published under.
`reuse_chains_across_generations_and_outlives_the_directory_it_came_from` exercises three
generations with a different pane dirty each time and asserts the pane untouched throughout keeps
its original bytes after both earlier directories are gone.

`rozi metrics` and the DevTools `Snapshot` row reported `last_exported_panes`,
`last_reused_panes`, and `last_exported_bytes`. These metrics linked a slow snapshot in the field
to its dirty-pane count without reproducing it.

### Reconciling the two changes

Taken alone, the asynchronous split produced a small improvement in the case that motivated it. The
split still moved a slow `write`, `sync`, or rename off the server loop. That source of unpredictable
latency differs from export cost and reuse does not address it. The split also established
generation-aware completion, publication after a successful write, bounded shutdown, capture and
persistence separation, and a blocking metric distinct from the total. Without the split, reuse
would have reduced CPU-bound export and left storage work on the loop.

The accurate summary of the two together:

> Asynchronous persistence removed fixed filesystem blocking and enabled correct background
> snapshot publication. Per-pane replay reuse eliminated the dominant redundant export work.

Snapshot cost went from roughly `O(all panes x retained history)` to
`O(dirty panes x retained history) + O(clean panes)`, where the second term is a hard link per
pane.

## Limitations and open work

- The server's fixed idle polling remained measurable. Adaptive backoff or readiness-driven waiting
  needed design and comparative latency measurement. Evaluation had to include key round-trip
  latency and idle cost.
- Configurable image-budget work remained gated on Phase 5 measurement and design.
- Resurrection snapshots wrote off the server loop and reused unchanged panes' replay files. This
  took the 16-pane 5,000-row case from roughly 208 ms of blocking to roughly 11 ms. A session where
  every pane was busy still exported every pane. Bounding persisted history was the remaining
  option, and slow-storage evidence was still missing.
- The server's fixed idle polling was re-examined without a change. Switching the loop's fast/slow
  predicate from "any connected client" to "any *attached* client" was rejected. Query and
  non-attached connections closed after flush (`set_close_after_flush`), so they lived one or two
  iterations. The change would have added up to 20 ms to every discovery probe and query response
  with no measurable idle saving.
- A long-duration/full memory soak was not run, so no leak conclusion follows from the smoke result.
- Standalone CI could not resolve the sibling path dependency at the measured revision.
- `tests/sidebar_keyboard_smoke.rs`'s
  `keyboard_navigation_suppresses_stale_row_hover_until_the_pointer_moves` fails at this revision.
  The failure existed in the baseline and was unrelated to this work. It fails identically, with
  the same two colors, at `a612172` - the commit before any performance change - when built against
  the same framework tree. It belonged to in-flight sidebar file-tree work spanning both
  repositories. No performance commit touched `src/view/sidebar/`, `src/view/pane.rs`, or theme
  code.
